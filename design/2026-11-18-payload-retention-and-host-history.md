# LLM call retention and host resource history

Admin Panel → System Settings controls how many UTC calendar days of request and response bodies to keep, including today. The initial setting is seven days. Call IDs, errors, usage, timings, token counts and costs remain available after expiry. Increasing retention applies to bodies that still exist.

On upgrade, the API begins migrating existing call bodies in batches of 64. Each batch moves retained bodies to daily PostgreSQL partitions and clears the inline fields in the same transaction. Expired legacy bodies are cleared in place. Take a backup before upgrading an installation that needs its older prompts. Allow space for the retained bodies, indexes and WAL during migration. PostgreSQL can reuse space freed inside the old table after vacuum. An immediate reduction in the size of the old relation on disk requires a separately planned rewrite. Future expiry drops whole partitions.

Admin Panel → Host resources shows CPU busy time, physical memory in use (total minus available), and filesystem space in use on the API's local filestore volume. A host with a separate PostgreSQL volume can have a different database disk utilization. The API writes one sample every five minutes to daily Parquet files in the local filestore's private `.host-history` directory. The chart offers up to 30 days from collection start, including across API restarts with a persistent volume. Housekeeping runs with the API. When multiple API hosts share the same filestore, set a distinct, stable `HELIX_HOST_HISTORY_NODE` on each host. The chart reads the history of the API node serving the request.
