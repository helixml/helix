## Overview

Recurring merge task with a mature playbook. What makes **this** window
different from every prior one:

1. **It is the biggest window in the series** — 709 commits / 38 days, versus
   002251's previous record of 409.
2. **Three planned merges never landed.** 002224, 002251 and 002265 were
   specced but not merged. This merge subsumes all three. Their specs are

3. **ACP jumps two majors: `0.14.0 → 2.0.0`** (plus a new transitive

4. **Textual conflicts are small: 9 files, 10 hunks** (measured with a scratch

The substance of the playbook lives in the prior specs; this document records
the measured delta and the decisions specific to this window.

### Planning technique worth reusing

Conflicts were enumerated **without touching the repo** by merging in a
disposable worktree:

```bash
git worktree add --detach /tmp/mergetest/wt main
cd /tmp/mergetest/wt && git merge --no-commit --no-ff upstream/main
git diff --name-only --diff-filter=U
for f in $(git diff --name-only --diff-filter=U); do echo "$(grep -c '^<<<<<<<' "$f") $f"; done
cd - && git worktree remove --force /tmp/mergetest/wt && git worktree prune
```

`git merge-tree --write-tree --name-only main upstream/main` gives the same
list even faster, with zero checkout cost.

## Merge Strategy

`git merge upstream/main` — never rebase, never squash. Preserves Helix history
and keeps conflict resolution traceable.

```bash
cd /home/retro/work/zed
git checkout main && git pull origin main
git checkout -b feature/002353-merge-latest-zed
# START the portingguide.md "## Merge 002353 (2026-07-27)" entry NOW — before resolving
git merge upstream/main
# Resolve conflicts one at a time; append a porting-guide bullet as EACH is resolved.
# Then: ACP 2.0 compile loop → audit auto-merged files → unit tests → E2E.
git push -u origin feature/002353-merge-latest-zed
```

### Conflict-resolution principles (carried forward)

1. **Preserve Helix behaviour by default.** Never let cfg-gated Helix code leak
   into an unconditional path.
2. **Retire, don't silently drop.** If upstream absorbed a Helix patch, drop the
   Helix copy and write an explicit retirement note.
3. **Prefer upstream ordering** for shared additive lists (model lists, feature
   lists, match arms) — smaller diff.
4. **`Cargo.lock`**: `git checkout --theirs`; regenerated by the next build.
5. **`Cargo.toml`**: take upstream's `agent-client-protocol = "=2.0.0"` pin.
   Keep Helix workspace members (`external_websocket_sync`, `cloud_api_types`)
   and `rust-embed`'s `debug-embed` feature.
6. **`.github/workflows/`**: Helix doesn't run GitHub Actions — keep the fork's
   deletions (see Open Question 7).
7. **Auto-merged ≠ correct.** After the merge, grep for old identifiers inside
   cfg-gated regions even in cleanly-merged files.
8. **Trait/`non_exhaustive` changes**: resolve compile-driven; the build is the
   safety net. Convert struct literals to builders.
9. **Document every non-trivial resolution in `portingguide.md` immediately.**
10. **If a conflict is too risky, stop and escalate** rather than guess.

### Systematic ACP repair procedure

1. Take upstream's `Cargo.toml` ACP pin; `git checkout --theirs Cargo.lock`.
2. Build (`./stack build-zed dev`) and work the error list from the bottom up.
3. For each `non_exhaustive` struct-literal error, convert to the builder form —
   upstream's `client_capabilities_for_agent()` in `agent_servers/src/acp.rs` is
   the canonical example of the ACP 2.0 idiom.
4. Check `acp::ErrorCode` match arms for new variants.
5. Grep for unit-variant `Stopped`:
   `grep -rnE "AcpThreadEvent::Stopped\b([^(]|$)" crates/acp_thread/src/` → must be 0.
   `#[cfg(test)]` code does not fail `cargo build` — it fails
   `cargo test -p acp_thread test_second_send`. Check both.
6. Append each repaired site to `portingguide.md` as you go.

returns **0 commits** while the file looks like the highest-risk file in the

`conversation_view/thread_view.rs`.

`thread_view.rs` when they mean `conversation_view.rs` — correct them.
