# Design: Merge Latest Zed Upstream Into Helix Fork

## Overview

Recurring merge task with a mature playbook (see
`helix-specs/design/tasks/002353_merge-latest-zed/design.md` for the full one).
This document records only the measured delta and the decisions specific to the
2026-08-10 window.

What makes **this** window different:

1. **It is the smallest window in the series** — 128 commits / 12 days, versus
   002353's 709 / 38 days. The prior merge landed, so there is no backlog.
2. **No ACP bump.** `agent-client-protocol` is `=2.0.0` on *both* sides, with
   `-derive 2.0.0` and `-schema 1.5.0` identical. The dominant work item of the
   last three cycles is simply absent.
3. **One textual conflict.** `crates/title_bar/Cargo.toml`, one hunk.
4. **The four highest-risk Helix files have zero upstream changes**:
   `conversation_view.rs`, `agent_servers/src/acp.rs`, `agent/src/agent.rs`,
   `acp_thread/src/connection.rs`.
5. **The real work is two structural upstream changes**: the
   `git_ui` → `git_ui_core` crate split, and the rustc `1.95.0 → 1.97.1` bump.

### Planning technique (reused from 002353, still the fastest)

Conflicts enumerated **without touching the repo**:

```bash
git merge-tree --write-tree --name-only main upstream/main
```

Zero checkout cost; prints the conflicted paths directly. The disposable
worktree variant (`git worktree add --detach /tmp/mergetest/wt main`) is only
needed when you want to read the actual conflict hunks.

## Merge Strategy

`git merge upstream/main` — never rebase, never squash.

```bash
cd /home/retro/work/zed
git checkout main && git pull origin main
git checkout -b feature/002701-merge-latest-zed
# START the portingguide.md "## Merge 002701 (2026-08-10)" entry NOW
git merge upstream/main
# Resolve title_bar/Cargo.toml → then git_ui_core migration (compile-driven)
# → then rustc 1.97 diagnostics → audit auto-merged files → unit tests → E2E.
git push -u origin feature/002701-merge-latest-zed
```

Given the size, a single merge round should suffice — no need for the multi-round
`round 1 / round 2 / …` staging that 002353 used for its 709 commits.

### Conflict-resolution principles (carried forward, unchanged)

1. **Preserve Helix behaviour by default.** Never let cfg-gated Helix code leak
   into an unconditional path.
2. **Retire, don't silently drop.** If upstream absorbed a Helix patch, drop the
   Helix copy and write an explicit retirement note.
3. **Prefer upstream ordering** for shared additive lists — smaller diff.
4. **`Cargo.lock`**: `git checkout --theirs`; regenerated by the next build.
5. **`Cargo.toml`**: keep Helix workspace members (`external_websocket_sync`,
   `cloud_api_types`) and `rust-embed`'s `debug-embed`; take upstream's new
   `crates/git_ui_core` member + `git_ui_core = { path = ... }` dep and the
   `ctor 1.0.6 → 1.0.12` / `windows-registry 0.6.0` changes.
6. **`.github/workflows/`**: Helix doesn't run GitHub Actions — keep the fork's
   deletions.
7. **Auto-merged ≠ correct.** Grep for old identifiers inside cfg-gated regions
   even in cleanly-merged files.
8. **Trait / crate-split changes**: resolve compile-driven; the build is the
   safety net.
9. **Document every non-trivial resolution in `portingguide.md` immediately.**
10. **If a conflict is too risky, stop and escalate** rather than guess.

## Work item 2: rustc `1.95.0 → 1.97.1`

Upstream's HEAD commit *is* the bump (#62395). `rust-toolchain.toml` goes
`channel = "1.95.0"` → `"1.97.1"`; it auto-merges (the fork does not modify it).

**Why it matters here:** `/home/retro/work/helix/Dockerfile.zed-build` installs
rustup with `--default-toolchain none` and lets `rust-toolchain.toml` pick the
version, with a BuildKit cache mount at `/root/.rustup`. So:

- The bump *should* be picked up with **no Dockerfile change**. Verify; do not
  assume.
- The `/root/.rustup` cache mount is warm with 1.95.0 only — the first build
  downloads a whole new toolchain plus the three cross targets
  (`wasm32-wasip2`, `wasm32-unknown-unknown`, `x86_64-unknown-linux-musl`).
- A toolchain change invalidates the entire Cargo build cache. **Budget for a
  cold full rebuild**, and do not interpret the long build as a hang.
- If 1.97.1 cannot install (base-image glibc, network), that is a Helix-repo
  change — escalate rather than pinning back to 1.95.0, which would diverge
  from upstream and break the next merge.

**Expected fork-only diagnostics.** Upstream pre-emptively changed
`rems_from_px(12.)` → `rems_from_px(12_f32)` in ~8 sites in
`conversation_view/thread_view.rs` (and `rems_from_px(-12.0)` →
`rems_from_px(-12.0_f32)`), which points at a float-literal inference ambiguity
the newer compiler rejects. Apply the same suffixing remedy to fork-only call
sites. Do not "fix" it by changing the API.

## Key decision: do not "restore" `trust_all_worktrees` / `show_sign_in`

Brief constraints #8 and #12 say these must be set in
`assets/settings/default.json`. They are not, and that is correct. Both were
re-implemented as feature-gated code some cycles ago:

| Constraint | Old implementation | Current implementation |
|---|---|---|
| #8 trust all worktrees | `"trust_all_worktrees": true` in `default.json` | `crates/project/src/trusted_worktrees.rs:469-474` — `if cfg!(feature = "external_websocket_sync") { … }` auto-trusts; plus `title_bar.rs:695-701` `render_restricted_mode()` returns `None` under the same gate |
| #12 hide sign-in | `"show_sign_in": false` in `default.json` | `crates/title_bar/src/title_bar.rs:379` — `&& !cfg!(feature = "external_websocket_sync")` |

**Rationale for keeping it this way:** `assets/settings/default.json` is a
~2500-line file upstream edits nearly every window (this window: 3 new keys).
Every Helix value in it is permanent merge surface. A `cfg!` gate in Rust is
compile-checked, invisible to the JSON diff, and cannot silently regress. Audit
the gates; leave the JSON at upstream's values. Recorded in the porting guide
and flagged in requirements Open Question 1 for confirmation.

## Lessons carried forward (for whoever clones this spec)

- **Merging on a short cycle is dramatically cheaper.** 709 commits / 38 days
  produced 9 conflicts and a two-major ACP bump; 128 commits / 12 days produced
  1 conflict and no protocol change. The series' single biggest risk factor is
  *letting a window go unmerged*.
- **`git merge-tree --write-tree --name-only A B`** enumerates conflicts with no
  checkout, no worktree, no repo mutation. Always start planning with it.
- **Measure per-file upstream churn before writing the audit list.** Half of the
  "high-conflict files" in the standing brief had zero changes this window;
  auditing them anyway wastes the budget that `extensions_ui.rs` needed.
- **Migrate Helix patches from config files into `cfg!` gates.** JSON/TOML
  defaults are permanent merge surface; compile-checked gates are not. Two
  standing brief constraints have already been retired this way.
- **A crate split is a bigger deal than a conflict count suggests.** One
  conflicted line in `title_bar/Cargo.toml` fronts a 13-file symbol migration
  and an API arity change.
- **A `rust-toolchain.toml` bump auto-merges silently and then invalidates every
  cache.** Look for it explicitly in the diff; it never shows up as a conflict.

## Out of Scope

See requirements. In short: no net-new Helix features, no E2E-assertion changes
(unless an upstream API change forces them), no upstreaming of Helix patches, no
Helix-crate refactors beyond what the merge and the `git_ui_core` split force,
and no adoption of upstream's elicitation / message-queue-steering / sandboxing
UX into Helix-mode flows beyond keeping them compiling.
