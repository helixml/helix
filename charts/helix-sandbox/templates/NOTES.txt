Runner identity:
  Deployment defaults seed from the pod name for old-image compatibility, then
  the updated image persists and reuses /hydra-data/.helix-runner-id. This
  automatic mode requires hydraData persistence and both the updated chart and
  runner image. On the first rollout of an existing runner, set
  sandbox.instanceId to its exact current ID: the old image did not store that
  ID locally, so a new pod name would break existing bindings. An explicit ID
  initializes the marker and must match it thereafter; removing the override
  reuses the stored ID. StatefulSet uses ordinal pod names and is unchanged.
  Do not share IDs or use one fixed ID with RollingUpdate; there is no automatic
  rebinding or cleanup of old runner records.

Connectivity:
  The sandbox uses RevDial to establish an outbound connection to the control plane.
  No inbound ports or LoadBalancer are required.

To check the status:
  kubectl get pods -l "app.kubernetes.io/name={{ include "helix-sandbox.name" . }}"

To view logs:
  kubectl logs -f -l "app.kubernetes.io/name={{ include "helix-sandbox.name" . }}"

To verify dockerd is running inside the sandbox:
  kubectl exec -it deploy/{{ include "helix-sandbox.fullname" . }} -- docker info

To check Hydra status:
  kubectl exec -it deploy/{{ include "helix-sandbox.fullname" . }} -- ls -la /var/run/hydra/

Troubleshooting:
  - If pods fail to start, check that privileged containers are allowed
  - Verify GPU nodes have the NVIDIA device plugin installed (for NVIDIA GPUs)
  - Check control plane URL and runner token are correct

Note: The sandbox requires privileged mode for Docker-in-Docker functionality.
Ensure your cluster's security policies allow privileged containers.
